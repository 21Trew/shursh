# Централизованный ручной Production-релиз Шурш

Workflow .github/workflows/production-release.yml запускается только через workflow_dispatch с защищённой main. Нет push/schedule/PR-триггера публикации. Код контроллера берётся из github.sha защищённой ветки, а не из релиз-кандидата. Локальный --apply запрещён. На момент разработки workflow НЕ активирован, настройки Vercel и GitHub не изменяются.

## Перед внедрением (отдельное разрешение)
- Перенести проверенный контроллер на main и защитить ветку, включая файлы workflow и tools; ограничить право изменения workflow. Не публиковать устаревшую main как приложение.
- Создать GitHub environments shursh-release-read и shursh-production, разрешить только ветку main. В shursh-production задать required reviewers (независимый reviewer), Prevent self-review, запретить admin bypass. Проверить доступность required reviewers на тарифе/видимости репозитория. Скрипт проверяет реальную запись одобрения и правила ветки через API, без них не публикует.
- В read environment установить VERCEL_RELEASE_READ_TOKEN с минимальным доступом к проекту; если Vercel не выдаёт read-only токен, считать его привилегированным и защищать environment соответственно. В production environment установить VERCEL_RELEASE_WRITE_TOKEN, при необходимости VERCEL_AUTOMATION_BYPASS_SECRET в обоих. Не хранить эти токены как repository secrets. GitHub token выдаётся отдельно на job, contents:write только в apply для журнала. Не включать SHURSH_RELEASE_ENABLED=true до отдельной приёмки.
- Создать отдельную служебную ветку release-journal (без кода приложения и workflow), в корне release-journal.json с ровно {"schema":1,"state":"idle"}. Разрешить запись только релизному контроллеру, запретить force-push/delete, исключить ветку из Vercel Git builds. Настроить и проверить, что GitHub Actions token может обновлять именно журнал. История Git хранит все состояния без токенов. Отсутствующий или повреждённый журнал блокирует работу. Не сбрасывать journal в idle для обхода аварии.
- До создания staged Production-сборки подтвердить отключение Auto-assign Custom Production Domains, отсутствие rolling release и синхронность доменов. Скрипт не изменяет настройки. Vercel может восстановить автоназначение при promotion; проверять его перед каждой сборкой. Отдельно исключить ручные promotion/alias и другие CI, не использующие этот механизм.

## Запуск
В Actions → Manual Production release выбрать main и operation. audit (apply=false, остальные поля пустые) проверяет текущие домены и Git без мутаций. Publish: указать полный SHA открытого PR, PR number, CI run ID (не номер #), ID READY staged Production deployment и expected_live (текущий deployment ID). Сборка кандидата остаётся отдельной ручной операцией с Production-окружением и без назначения доменов; workflow сам ничего не собирает и не мигрирует.

Сначала apply=false. Для публикации выбрать тот же набор значений, apply=true и confirmation PUBLISH <полный SHA>. Plan выполняется повторно до job apply; apply ждёт независимого environment review, снова проверяет SHA, CI, baseline, домены и candidate bytes. Секреты мутации только в apply. Workflow использует общую concurrency group с cancel-in-progress:false для audit/publish/rollback, включая ожидание review. GitHub может заменить ещё не начатый pending run, но не отменяет активный. Не отменять активный запуск вручную. Повтор failed job запрещён: новый dispatch после диагностики.

## Журнал и восстановление
До Vercel POST в центральный Git-журнал атомарно записывается prepared с SHA, deployment IDs, инвентарём, хэшами и run ID. Обновление с ожидаемым blob SHA, конфликт или непроверенная запись блокируют переход. При успешном smoke записывается published; при подтверждённом автоматическом откате rolled-back; при неопределённом результате rollback-required (при аварии runner останется prepared). Любой следующий publish блокируется до восстановления. Журнал и Actions log — источник истории, не runner filesystem. Не содержит секретов.

Rollback: operation=rollback, SHA предыдущего релиза из журнала, expected_live=ID candidate из того же журнала; остальные поля пустые. Dry-run сначала. Для мутации apply=true, confirmation ROLLBACK <SHA>, независимое approval. Сверяются сохранённый baseline с Git, фактические aliases, состояние проекта и receipt Vercel. Если предыдущее состояние уже восстановлено и подтверждено, проверяется без лишнего POST. Неизвестный/pending переход блокирует recovery до выяснения состояния; не посылать слепой повторный POST. При failed smoke автоматический rollback входит в явно одобренную транзакцию publish. Если есть внешняя операция, инструмент останавливается. Нужна ручная диагностика, если журнал/настройки/домены повреждены или API недоступен.

Ограничения: concurrency сериализует только этот workflow в данном репозитории; прямые действия администратора/Vercel не блокируются технически, требуются ограничения доступа. Нет серверного compare-and-swap у Vercel между GET и POST. Git-журнал защищает cooperating clients, не злонамеренного администратора. Contents:write у стандартного GITHUB_TOKEN имеет репозиторный scope, а не scope одной ветки; доверенная main и branch rules обязательны. Для более строгой изоляции возможен отдельный репозиторий журнала/ограниченный GitHub App. Приёмка на изолированном проекте с реальными approvals, journal, promotion и rollback обязательна до активации Production. Авторизованный пользовательский smoke остаётся отдельной проверкой. Никаких миграций или merge данный инструмент не выполняет.
