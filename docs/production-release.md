# Ручной Production-релиз Шурш

Никакого deploy по push/merge в рамках этого инструмента. Для запуска нужен Node.js 22+, проверенный checkout этого release-инструмента и токены GH_TOKEN (чтение repo/actions) и VERCEL_TOKEN (только нужная команда/проект); настрой их локально, не коммить и не передавай в командной строке. Если staged deployment защищён, VERCEL_AUTOMATION_BYPASS_SECRET нужен только для его URL. Не отключать Deployment Protection.

## Подготовка (однократно, вручную)
В Vercel Project Settings отключить Auto-assign Custom Production Domains. Проверить, что все Production-домены находятся в одном проекте shursh, www перенаправляет на shursh.fun, Preview/Staging не используется как Production. Ограничить доступ к ручному Promote/Alias; не использовать ручные алиасы после внедрения. Настройка не меняется данным скриптом. Нельзя гарантировать блокировку стороннего администратора только кодом локального скрипта.

## Релиз
1. Выбрать полный SHA текущего открытого PR; пройти полный CI. Создать staged Production deployment из точного Git SHA (не Preview; автоназначение доменов отключено). Проверить метаданные Git и READY; не назначать домены. Не запускать миграции.
2. Предварительная проверка, без изменений Production:
   `node tools/publish-production.mjs publish --sha <40hex> --pr <number> --run <GitHub-run-ID> --deployment <dpl_ID>`
3. Только после явного разрешения на конкретный SHA повторить ту же команду с `--apply`. Все проверки выполняются заново. Инструмент делает один project-level promote, проверяет полный инвентарь доменов, их aliases, редиректы, идентичность SHA-256 UI-файлов с Git, HTTP и безопасный отказ старых маршрутов. При неуспешном smoke откатывает весь проект, а не отдельные домены, и проверяет предыдущие хэши. GitHub Actions ничего не публикует.
4. После релиза провести ручную авторизованную приёмку; анонимный smoke не заменяет её.

## Откат
`node tools/publish-production.mjs rollback` — план; с `--apply` — откат на сохранённый предыдущий Production. Журнал без секретов находится в ~/.shursh-release/journal.json, локальный lock препятствует параллельному запуску на одной машине. В случае crash проверить состояние доменов, затем удалить оставшийся lock только после подтверждения, что другой процесс не работает. При внешнем конкурирующем релизе скрипт прекращает изменения. Если rollback не подтверждён, статус rollback-required, требуется ручная диагностика. Нельзя одновременно выполнять релизы с разных машин/консолей. Для централизованной межмашинной блокировки в будущем можно перенести проверенный инструмент в защищённый workflow_dispatch с concurrency и approval; не включено в текущем PR.

Никаких изменений БД, Auth, веток или merge. Для релизов с миграциями нужна отдельная процедура; текущий механизм блокирует такие diff.
