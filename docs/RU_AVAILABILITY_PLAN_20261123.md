# Доступность Шурш из России: диагностический план (23.11.2026)

## Что подтверждено
- Production: https://shursh.fun -> Vercel, Flask в `fra1`; Supabase Production находится в `eu-central-1`.
- Frontend запрашивает основные `/api/*` через тот же origin, а Python-бэкенд обращается к Supabase.
- В `public/index.html` подключена блокирующая таблица стилей Google Fonts (Onest/Unbounded).
- Подтверждённых измерений из российских провайдеров пока нет; наличие проблем с Vercel у других проектов не доказывает причину для этого домена.
- Ни VPN, ни доверенность к российским IP-адресам по HTTP-логу не заменяют реальную диагностику.

## Как отличить первопричины
1. Сравнить без VPN в 3–4 независимых сетях РФ (домашний провайдер, МТС, Билайн/МегаФон, другой город) `shursh.fun`, `shursh.vercel.app`, `/app.js`, `/polish.css`, `/api/me` и Google Fonts.
2. Использовать `node tools/ru-network-probe.mjs` на машине в каждой из сетей. В отчёте сохраняются только DNS, HTTP-код, время ответа, объём ответа и коды сетевых ошибок. Нет паролей, cookies или тела ответа.
3. Ошибки TLS/TCP на `/` до HTTP-ответа -> сначала проверять Vercel ingress, DNS и маршрут провайдера. HTML отдаётся, но ждёт Google CSS -> критический внешний ресурс. HTML и CSS работают, а `/api/me` не работает -> анализировать Server-Timing, Flask и доступ к Supabase из `fra1`.
4. Повторять в несколько часов и по мобильной сети: единичный успешный запрос не доказывает устойчивую доступность.

## Варианты исправления (по возрастанию риска)
- **Быстрый:** self-host `.woff2` для Onest и Unbounded (с лицензией SIL OFL), убрать блокирующий запрос к Google Fonts после проверки скриншотов и CLS. Не помогает, если не проходит соединение с самим Vercel.
- **Промежуточный:** тестовый зеркальный Flask-деплой на RU-доступном хостинге с **только Supabase Staging** и отдельным тестовым hostname. Проверить HTTPS, регистрацию/confirmation callback, изображения, SSE/пулы соединений (если используются), долгие ответы и расходы.
- **Рекомендуемый при подтверждённом отказе Vercel:** перенос основного ingress/приложения на проверенный доступный из РФ хостинг, резервное сохранение Vercel. Supabase Production и SMTP временно не менять; сначала проверить маршруты российского сервера к DB/Auth и требования к обработке персональных данных.
- **Если нужно**: два независимых провайдера и контролируемый DNS failover после отдельного теста согласованности сессий. Система резервирования без мониторинга и репетиций отката — не гарантия доступности.

## Критерии перехода
- Зелёные CI, Chromium/WebKit, проверка регистрации, ссылок подтверждения, выхода, Тайного Санты и вишлистов в Staging.
- Повторяемые положительные измерения по разным РФ-провайдерам; исключены ошибки DNS/TLS, 5xx и зависание загрузки.
- Не менее 7 дней доступности под наблюдением, с заранее выбранными целевыми порогами.
- Письменное одобрение изменения DNS, Production Auth/URL, инфраструктуры и расходов.

## Откат
- До переключения сохранить текущие DNS и Vercel alias/deployment ID, установить разумный TTL.
- Если новый ingress неудовлетворителен — вернуть DNS/алиасы на предыдущий Vercel Production, не трогая Production DB.
- Не переносить и не копировать Production-данные в тестовые среды. Не отключать старый origin до подтверждения здоровья нового.
