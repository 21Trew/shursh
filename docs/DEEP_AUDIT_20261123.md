## Безопасность: проверенные защитные механизмы

- Все **21** пользовательские таблицы в \`public\` имеют RLS. У \`anon\` и \`authenticated\` нет прямых SELECT/INSERT/UPDATE/DELETE на эти таблицы. \`public\` не содержит выполняемых этими ролями пользовательских функций.
- Backend \`shursh_backend\` привилегирован внутри доверенного Python-слоя; RLS **не заменяет** проверки владельца, участника и администратора в каждом API.
- Сессии: хешированный cookie-токен; \`HttpOnly\`, \`Secure\`, \`SameSite=Lax\`, срок 24 часа. Авторизация Supabase подтверждается upstream, а user_metadata используется только для отображения.
- Статические ответы и API защищены CSP, no-sniff, no-referrer, no-frame; API не кэшируется.
- Ограничение частоты запросов: отдельные лимиты на вход, повтор подтверждения, чат, обратную связь. Ошибка неправильных логина/пароля не перечисляет существующие аккаунты.
- Существующие CI-сценарии проверяют разграничение доступа к приватным вишлистам, броням, Санте, личным ссылкам и каталогу админки.

**Утечка пользовательских данных не подтверждена.** Это точная формулировка, а не гарантия полной безопасности.

## Производительность

- Анонимные \`/api/me\` и \`/api/dashboard\` отдают безопасный ответ без открытия соединения с БД, если нет cookie.
- Авторизованные owner-навигационные данные кэшируются в клиенте; в CI есть проверка отсутствия HTTP при warm navigation.
- PostgreSQL использует маленький пул и Supavisor; каждый rate-limit write требует отдельного SQL, что является возможной стоимостью высокого RPS.
- Реальные задержки из РФ — отдельное нерешённое инфраструктурное ограничение. Пользователь решил **пока оставаться на Vercel**, к REG.RU/Timeweb вернуться при необходимости.
- Размер хранилища изображений ограничен кодом (\`IMAGE_TOTAL_LIMIT = 100000000\` байт). При росте числа пользователей понадобится отдельное хранение файлов и политика жизненного цикла; сейчас \`wish_images\` имеет 0 записей.
- Не проводить преждевременное дробление JS, индексацию всех FK или замену бэкенда без измеряемого выигрыша.

## Отдельная задача: валидация входа и регистрации

Реализуется в Draft PR #13, независимо от Production:

- Регистрация: имя (1–40 знаков, без управляющих символов), корректный email, пароль 8–200 символов, повтор пароля.
- Вход: email и пароль с теми же допустимыми длинами, без усложнения требований для уже существующих пользователей.
- Сообщения прямо под полем, ошибки по blur и submit, на исправлении сбрасываются. Доступность: \`aria-invalid\`, \`aria-describedby\`, фокус.
- Проверка на сервере вне зависимости от JS; пароль не обрезается и не записывается в логи; проверка наличия аккаунта не проводится.
- Генератор пароля синхронизирует поле повтора и сохраняет возможность копирования в менеджер паролей.
- Никаких изменений Supabase Auth settings, схемы БД, email-шаблонов или Production в этой задаче.
