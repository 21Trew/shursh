# UX / responsive audit — Шурш! PR #4

Scope: анализ реализации текущего PR #4, существующих браузерных тестов и Gallery
Источники: `DESIGN.md`, `public/app.js`, `public/social-ui.js`, `public/santa-ui.js`,
`public/styles.css`, `tests/test_cloud.py`, `tests/test_pr4_acceptance.py`
Это аудит по коду + CI, а не подтверждение ручной приёмки всех браузеров на реальных устройствах

## Подтверждённые наблюдения по исходникам

**P0 — стабильность и приватность**

- Обходы приватных вкладок кешируются как DOM и отдельные API-данные; сохранять эту модель
- Публичные bearer-маршруты исключены из owner-cache; не смешивать private/public компоненты
- Модалки с длинными формами имеют особые ограничения height/scroll; любое общее правило
  для dialog проверять отдельными E2E на 375 и 390 px
- Рисунок `✳` ранее отображался как emoji на iOS; в карточках игр уже SVG
  Добавление новых псевдоэлементов с unicode-символами требует визуального review на WebKit

**P1 — визуальное единообразие**

- Реестр CSS на текущей ветке фиксирует повторяющиеся селекторы и расхождения значений
  Такие случаи, как `.modal`, `.header-bell`, `.nav` и `.game-chat-tabs`,
  требуют консолидации после скриншотной проверки; удалять их вслепую нельзя
- `.btn-small` и иконки имеют отдельные компактные размеры: проверять 44px touch targets,
  особенно рядом с переключением чатов и бронями
- Встречаются одновременно 12px/13px подписи и стили muted; проверять
  контраст и доступность, не уменьшать шрифт ради экономии высоты
- Длинные вкладки чатов и слайдеры должны горизонтально прокручиваться внутри
  родителя, а не расширять страницу
- Галерея фиксирует пять ширин вместо сравнения только desktop/mobile

**P2 — сопровождение**

- `ARCHITECTURE.md` содержит исторический текст об initial SQLite MVP,
  тогда как текущий проект использует Flask + PostgreSQL/Supabase; документация нуждается
  в отдельной редакции, без изменения БД в рамках UI задачи
- Реестр содержит ожидаемые responsive overrides. Он диагностический:
  количество конфликтов не равно числу пользовательских дефектов

## UX принципы для следующих итераций

1. Первое действие должно быть видно без прокрутки на 375px, когда это возможно
2. Одна основная CTA на экран / карточку, вторичные действия визуально тише
3. Присутствуют loading / empty / error / success состояния без декоративного шума
4. Успешное действие обновляет только затронутый фрагмент; сервер не блокирует уже открытый раздел
5. Никакой повторной отрисовки общего header/footer из-за изменения соседнего поля
6. `prefers-reduced-motion`, фокус, кликабельность и scrollbar — часть UX, а не украшение

## Какой результат подтверждён тестами

Существующие E2E покрывают авторизацию, часть social, Santa и wish-list сценариев,
навигирование, мобильные формы, HTTP/DOM-замеры на 375/390/768/1440
Новые Gallery проверки добавляют 1024, computed-style baseline, keyboard/modal semantics,
регрессию viewport и screenshot artifacts

**Не подтверждено автоматически:** субъективная композиция и ощущение плавности на
реальном iPhone Safari, VoiceOver, все сценарии администратора с реальными данными
Их стоит принять вручную после просмотра скриншотов. Это не основание задерживать
документирование уже существующего UI-kit
