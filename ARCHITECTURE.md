# ARCHITECTURE — Шурш! MVP

## Почему Python + SQLite, а не Next.js + Supabase

Цель текущей поставки — скачать и запустить без ключей, платных услуг, миграций внешней базы и npm-сборки. Для однопроцессного локального MVP стандартная библиотека Python и SQLite дают атомарные транзакции, простой запуск и воспроизводимые тесты. Это **осознанное отклонение** от предпочтительного будущего стека Next.js/React/Supabase. На публичный сервис эту реализацию без дополнительного hardening переносить нельзя.

## Компоненты

- `server.py` — `ThreadingHTTPServer`, JSON API, маршруты, сериализация, валидация, cookies, `sqlite3`.
- `public/app.js` — роутинг на клиенте через History API (или hash для file-превью), формы, модальные окна, уведомления, иконки/иллюстрации.
- `public/styles.css` — дизайн-токены, responsive breakpoints, состояния элементов.
- `public/preview-store.js` — автономный локальный симулятор для одного браузера; **отдельно от настоящего API**.

## Модель данных

- `users`, `sessions`: аккаунты, scrypt-хеши паролей, SHA-256-хеши cookie-токенов, срок жизни.
- `wishlists`: владелец, `share_key`, `visibility`, описание, оформление.
- `wishes`: подарки и впечатления, картинки, магазин/цена/валюта/приоритет.
- `reservations`: `wish_id`, `manage_hash`, отмена через `cancelled_at`; **уникальный индекс на `wish_id` только для активных броней**.
- `santa_events`: организатор, `invite_key`, статус `open/drawn`, дата, бюджет, правила.
- `participants`, `participant_wishes`: гости и их пожелания, SHA-256-хеш приватного ключа гостя.
- `exclusions`: направленные пары `giver_id → receiver_id`.
- `assignments`: уникальность дарителя и получателя в одном событии, время раскрытия.

`init_db()` создаёт таблицы и индексы при первом запуске. Для следующей версии нужны версионированные SQL-миграции; здесь схема начальная и обновления БД миграциями пока не обеспечены.

## Инварианты и границы доступа

- Владелец через `GET /api/lists/{id}` получает желания без каких-либо полей брони. Для авторизованного владельца `GET /api/public/{share}` также не передаёт состояние бронирований.
- Анонимный гость по публичному URL получает лишь boolean `reserved`; имя дарителя и токен не отдаются.
- Бронь делается под `BEGIN IMMEDIATE`; частичный уникальный индекс блокирует гонки конкурентных запросов.
- Отмена только по bearer-токену, в БД хранится его SHA-256.
- Администратор Санты видит состав, числа пожеланий, ограничения; таблицу назначений не видит.
- Участник по приватному токену получает только свою запись. До раскрытия сервер возвращает `{revealed:false}`.
- После `draw` состав и исключения заморожены; повторный `draw` не меняет назначения.
- Для `n ≤ 12` алгоритм DP считает число допустимых биекций и выбирает равновероятную полную конфигурацию через `secrets.randbelow`. Самоназначения и исключения отсекаются.
- Все чувствительные операции проверяются на сервере. JSON не выполняется, пользовательские тексты в клиенте HTML-экранируются, URL магазина валидируется по протоколу и структуре.
- Секретные ссылки защищены `Referrer-Policy: no-referrer`, сессионные cookie — `HttpOnly; SameSite=Lax`, `Secure` включается конфигурацией `SHURSH_HTTPS=1` при HTTPS.

## Не решено для production

Аудит аутентификации и abuse protection, полноценная email-верификация, безопасное восстановление ссылок, rate limiting в общем хранилище, резервные копии, security headers для внешних ресурсов, масштабирование и RLS при использовании Supabase/PostgreSQL. Сайт намеренно слушает только 127.0.0.1.

## Облачный адаптер

Flask `app.py` вызывает общие бизнес-маршруты `server.Handler` через
`cloud.backend.CloudRequest`. `cloud.db.transaction` использует psycopg,
транзакции READ COMMITTED для записей (единый advisory xact lock MVP) и
REPEATABLE READ READ ONLY для чтений. SQL с параметрами сохраняет прежний
контракт. Не допускается commit посреди операции. Ограничение скорости —
отдельная транзакция; счётчик увеличивается даже при неуспешном запросе.
Приватные токены хешируются; сессионная cookie HttpOnly, Secure, SameSite=Lax.
Supabase Auth используется для проверки пароля и подтверждённой почты;
метаданные пользователя — только отображаемое имя. Клиентские роли anon и
authenticated не имеют доступа к прикладным таблицам; сервер переключается
на роль shursh_backend. RLS защищает таблицы от прямого клиентского доступа,
прикладной сервер отвечает за авторизацию владельцев и гостевых ссылок.
Сессии приложения независимы от refresh-токенов Supabase, TTL 24 часа.
До production требуется выделенный DB login, ревокация сессий, SMTP и аудит.
